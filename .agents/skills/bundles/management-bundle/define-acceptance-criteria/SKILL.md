# 📋 受け入れ基準（AC）とエッジケースの定義

## 🎯 スキルの目的

スプリントで開発する機能（タスク）に対して、「何をもって完了とするか（Definition of
Done）」を明確にするためのスキルです。 各タスクの `[タスク実行時の役割]`
が迷いなく実行と検証を行えるよう、具体的な受け入れ基準（Acceptance
Criteria）と、考慮すべきエッジケースを網羅的に洗い出します。
このフェーズではコードの実装は一切行いません。

## 🔄 実施フロー

### 1. タスクと目的の確認

- **プロダクトバックログ** ([product-backlog.md](../../../../management/product-backlog.md))
  から、**スプリントバックログ** を確認し、今回のスプリント対象のタスクを確認します。
- ユーザーストーリー（誰が・何を・なぜ）とスプリントゴールを再確認し、タスクの目的から逸脱しないようにします。

### 2. 受け入れ基準（AC）の洗い出し

各タスクに対して、以下の要素を満たす AC を定義します。

- **機能的要件**: ユーザーが実行できる正常系の操作と期待される結果。
- **非機能的要件**: パフォーマンス、セキュリティ、デザイン等の制約（必要に応じて）。

### 3. エッジケースと「実効価値」の検証

各タスクに対して、予期せぬ入力や例外状況（異常系）を定義します。また、システム的にエラーにならなくとも実質的な価値を生まない
**「無価値な正常系（動くだけの無駄・見せかけの充足）」** を排除するための基準を設けます。

- **異常系のエッジケース**:
  不正な入力値、ネットワークエラー、依存サービスのエラー、境界値のテストなど。
- **実効価値のエッジケース（無価値な正常系の排除）**:
  - **手動多重度（UXの破綻）**:
    「自動化されたが、結果として人間側の手動確認や調整のステップが多すぎて自動化の意味がほぼない」状態になっていないか？
  - **表層的な成果物品質（低品質な生成など）**:
    「AIがドキュメントやコードを自動出力したが、内容が不正確で実用に耐えない（人間がすべて作り直す羽目になる）」状態になっていないか？
  - **複雑性の引き換え**:
    「機能自体は動くが、それによってシステムの保守・学習コストが異常に高くなり、中長期的に負債になっている」状態になっていないか？
  - **対策**:
    これらを「価値的失敗（実効価値のない正常系）」としてアンチパターンに定義し、回避するための具体的な合意基準をACに含めます。

### 4. ドキュメントの更新と承認

- 洗い出した AC とエッジケースを、バックログファイルのタスク詳細部分に追記します。
- ユーザーに内容を報告し、追加や修正がないか確認して合意（承認）を得ます。

### 5. 完了宣言

- 更新が完了したら、期待される結果を満たしたことを示すため、更新エビデンス（各タスクに追記されたACおよびエッジケースの差分など）を提示して完了を宣言します。

## ⚠️ 注意事項

- 本スキルを実行中は、**いかなるプログラムの実装や PR 作成、環境操作も行わないこと**（"No
  Development" ルール）。
- あくまで「指名された自身の専門役割」として、品質ACの策定と合意形成に徹すること。
