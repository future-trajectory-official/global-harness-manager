# Session Planning Skill

特定されたWork Packageに対し、文脈から判断された最適な専門家が、具体的な解決策と手順を
`implementation_plan.md`（アーティファクト）としてまとめるためのスキルです。

## インストラクション

1. **設計意図の確認**:
   - 実装計画の策定に先立ち、PO（ユーザー）に対して以下の設計意図を確認する質問を投げかけてください。
     - **採用技術**: 使用すべきフレームワーク・ライブラリ・言語バージョン等に指定はあるか
     - **配置規則**: ファイル構成・ディレクトリ構造・命名規則等に従うべきルールはあるか
     - **命名規約**: 変数名・関数名・クラス名等の命名に統一すべき規約はあるか
   - PO
     から明示的な回答や指定がない場合は、既存のコードベースのパターンに従うことを明記し、次のステップへ進んでください。
   - **git追跡対象外ファイルの確認**:
     `.gitignore`を確認し、編集対象となるディレクトリ・ファイルパターンのうちgit追跡対象外（`git ls-files`で認識されない）のものを把握してください。追跡対象外のファイルは既存コード調査時にgrep等で発見できないため、glob/file検索も併用して存在を確認します。
   - **既存コードの確認**:
     grep等で編集対象となる既存コードを検索し、実際の実装パターン・命名規則・配置規則を事前に把握してください。追跡対象外のファイルがある場合はglob/file検索も併用し、コードベースの全体像を見落とさないようにしてください。POから指定がなくとも、コードベースに既存の規約があればそれに従うことを計画に明記してください。

2. **設計の立案**:
   - ワークフローの例示に盲目的に従うのではなく、Work
     Packageの性質から「自身が今どの専門ロールとして振る舞うべきか」を動的に判断し、その知見を活かしてWork
     Packageを最小ステップの作業に分解します。
   - WPの種別に応じて以下のように異なる計画アプローチをとること：
     - **`WP_0`**（スパイクWP）の場合 →
       [references/spike-application.md](/.agents/skills/bundles/management-bundle/session-planning/references/spike-application.md)
       のケースAを参照し、調査計画を策定する。
     - **`WP_M'`**（スパイク後本実装WP）の場合 →
       [references/spike-application.md](/.agents/skills/bundles/management-bundle/session-planning/references/spike-application.md)
       のケースBを参照し、スパイク結果を計画に反映する。
     - **上記以外**で技術的不確実性が認められる場合 →
       [references/spike-application.md](/.agents/skills/bundles/management-bundle/session-planning/references/spike-application.md)
       のケースBを参照し、POにスパイクWP（`WP_0`）の分離を提案する。
3. **実装計画の作成**:
   - 以下の内容を含む `implementation_plan.md` を **アーティファクト** として作成してください。
     - 目的と概要
     - 受入基準 (AC) / 完了の判断基準
     - 具体的な作業ステップ（使用するツール、編集対象ファイル、検証方法） - セルフチェック項目

4. **多視点自己検証**:

指定されたレビュー推奨ロールの視点で、計画を自己検証します。以下の手順で実施します。

1. **推奨ロールの特定**:
   出力テンプレートの「レビュー推奨ロール」フィールドを参照します。未指定の場合はデフォルトロールとして
   `technical-advisor` を使用します。

2. **ルールファイル参照（推奨）**: 該当するロールのルールファイル（例:
   `/.opencode/agents/architect.md`）を参照し、そのロール固有の検視点を理解します。

3. **懸念点の抽出**: 各ロールの視点から、計画のリスク・トレードオフ・改善点を抽出します。

4. **結果の抑制**: 抽出された懸念点が5件を超える場合は、重要度順にTOP5に絞り込みます。

5. **結果の追記**: 検証結果を `implementation_plan.md`
   内の「多視点検証レポート」セクションにロール別の個別記載フォーマットで追記します。

検証で抽出された懸念点のうち是正すべきものは、計画に反映した上で「検証結果の反映」として記録します。

5. **PO への提示と待機**:

- 計画を提示し、「この計画で進めてよいか」を PO に問いかけてください。
- **PO の承認を得るまで、決して実装フェーズ（コードの書き換え等）に移行しないでください。**

6. **承認後の `task.md` 作成**:

- PO の承認を得たら、[task-template.md](/.agents/management/task-template.md) を参照し、 `task.md`
  をアーティファクトとして作成してください。
- **GUARD ブロックの除去**: `task-template.md` には `<!-- ... -->` で囲まれた GUARD ブロック
  （`GUARD:REQUIRED_H2` 等を含む）が定義されています。このブロックはテンプレート定義専用です。
  `task.md` を作成する際は、GUARD ブロック全体を必ず削除してください。削除せずに `task.md`
  に残すと、 後続の構造検証でエラーとなります。 - AC
  は計画時点で判明している内容をすべて記載してください。

7. **作成した `task.md` の構造検証**:

- 以下のコマンドを実行し、`task.md` がテンプレートの GUARD
  宣言（不変構造）に準拠していることを確認してください。
  ```
  deno task validate-task <task.mdのパス>
  ```
- 検証は `task-template.md` の `GUARD:REQUIRED_H2`、`GUARD:REQUIRED_H3`、`GUARD:REQUIRED_METRICS`
  を動的にパースして行われます。テンプレートを拡張・変更した場合は、GUARD
  ブロックも併せて更新することで検証ルールが追従します。
- 検証が通らない場合は、エラーメッセージに従って `task.md` を修正し、再検証してください。
