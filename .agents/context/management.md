# 3階層スコープモデル管理定義

本ドキュメントは、Global Harness Manager が提供する**管理概念の不変定義（配布対象）**です。
AIとPOの共有言語（用語集）を定着させ、用語解釈の齟齬を減らすことを目的とします。

> **位置づけ**
>
> - **本ファイル (management.md)**:
>   本ハーネスが提供する管理概念の**不変定義**。git追跡対象・配布対象。
> - **`product.md`**: 各リポジトリ特有の用語・具体定義。git追跡対象外・利用者編集。
>
> 本ファイルは管理概念の「定義の正」を担う。改訂時は本ファイルの定義を一意の追跡元とする。

---

## 1. 3階層スコープモデル

本ハーネスは、作業の粒度・ゴール設定・状態記録を一貫して管理するため、**3階層スコープモデル**を提唱する。
上位層が下位層の方向性を定義する階層構造である。

### 1.1. 三層構造

仕事の管理を3つの階層に分け、それぞれが異なる時間軸で運用する。

| 階層           | 時間軸               | 管理対象                                               | 代表的な概念                               |
| -------------- | -------------------- | ------------------------------------------------------ | ------------------------------------------ |
| プロジェクト層 | 長期（四半期〜数年） | プロジェクトの理念・方向性・規模の分類                 | Vision / Product Goal / Epic / Feature     |
| スプリント層   | 短期（数週間）       | 各スプリントでのゴール、価値の最小単位、検証・振り返り | Sprint Goal / PBI / Review / Retrospective |
| セッション層   | 単位（1回の作業）    | 1回の作業（セッション）で実行する最小の実装単位        | WP (Work Package)                          |

- **プロジェクト層**: 中長期的な方向性を定義する。頻繁に変わらない。
- **スプリント層**: プロジェクト層の方向性に沿った、一定期間の開発単位。
- **セッション層**: スプリント層のゴールを、実際の作業（1セッション）に分解する。
- 上位層が下位層の「存在理由（Why）」を定義し、下位層が上位層の方向性を具体化する。

### 1.2. 9つの概念

3階層スコープモデルには以下の **9概念** が存在する。

| 階層           | # | 概念          | 説明                                      | 具象化タイミング                                   | 変更頻度               | 管理者         |
| -------------- | - | ------------- | ----------------------------------------- | -------------------------------------------------- | ---------------------- | -------------- |
| プロジェクト層 | 1 | Vision        | プロジェクトが中長期的に目指す理念        | プロジェクト開始時                                 | 四半期に一度程度       | PO             |
| プロジェクト層 | 2 | Product Goal  | 現在取り組むべき具体的な到達目標          | プロジェクト開始時またはピボット時                 | 数スプリントに一度     | PO             |
| プロジェクト層 | 3 | Epic          | 複数PBIを束ねる大規模機能領域             | 必要に応じて                                       | 低                     | PO / Tech Lead |
| プロジェクト層 | 4 | Feature       | Epicに属する機能単位                      | 必要に応じて                                       | 低                     | PO / Tech Lead |
| スプリント層   | 5 | Sprint Goal   | 各スプリントで達成すべき短期的な目標      | 各スプリント開始時                                 | スプリント単位         | PO             |
| スプリント層   | 6 | PBI           | Sprint Goalを達成するための価値の最小単位 | バックログリファインメント時またはスプリント計画時 | スプリント単位         | PO             |
| スプリント層   | 7 | Review        | スプリントレビューの枠組み                | スプリント開始時                                   | スプリント終了時に更新 | PO             |
| スプリント層   | 8 | Retrospective | スプリント振り返りの枠組み                | スプリント開始時                                   | スプリント終了時に記入 | チーム全体     |
| セッション層   | 9 | WP            | PBIを分解した最小の実装単位               | スプリント計画時またはセッション開始時             | セッション単位         | AI（人間承認） |

### 1.3. 概念間の階層関係

二つの異なる観点の階層が存在する。

#### 目的の階層

```
Vision → Product Goal → Sprint Goal → PBI → WP
```

上位の概念が下位の概念の「存在理由（Why）」を定義する。

| 関係                       | 意味                                      |
| -------------------------- | ----------------------------------------- |
| Vision → Product Goal      | Visionを達成するための具体的な到達目標    |
| Product Goal → Sprint Goal | Product Goalに貢献する短期的な目標        |
| Sprint Goal → PBI          | Sprint Goalを達成するための価値の最小単位 |
| PBI → WP                   | PBIのACを実現するためのワークパッケージ   |

#### 分類の階層

```
Epic → Feature → PBI
```

プロジェクトが大きくなった場合に、PBIを意味的にグループ化するための階層。
Epicは必ずFeatureを介してPBIを保有し、Epicが直接PBIを持つことはない。

#### 参照ルール

- PBIは目的の階層と分類の階層の両方に同時に属する。
- WPは必ず1つの親PBIを持つ（親なしのWPは存在しない）。

## 2. 各概念の定義

### 2.1 Vision

プロジェクトが中長期的に目指す理念。全判断基準の根幹。変更は稀。

- **要件**: プロジェクトの理念を複数の観点から構造化して記述する。変更履歴の追跡が可能であること。
- **属性**: タイトル / 本文（対象ユーザー・提供価値・差別化要因・アウトカム）/ 変更履歴。

### 2.2 Product Goal

ビジョン達成に向けて現在取り組むべき具体的な到達目標。数スプリントに一度更新される。

- **要件**: 現在のゴール文の明示と、過去のゴール変更の履歴追跡。
- **属性**: タイトル / 本文 / 変更履歴。

### 2.3 Sprint Goal

各スプリントで達成すべき短期的な目標。Product Goalから導かれる。

- **要件**:
  スプリントの目的を表現する。期限は任意（品質やスコープを優先する場合は設定しなくてよい）。
- **属性**: タイトル / 説明文 / 開始日 / 期限（任意）。

### 2.4 Epic

同じビジネス概念やユーザーゴールに属するPBI群を束ねる論理的なグループ。必須ではない。

- **導入するケース**: 複数のPBIが「認証」「課金」「通知」等の同一の意味領域に属する場合。
- **導入しないケース**:
  PBIが互いに独立した意味領域に属し、フラット管理でも俯瞰性が損なわれない場合。
- **属性**: タイトル / 本文（概要・スコープ・完了定義）/ 子Featureへの参照。

### 2.5 Feature

Epic内のPBIをさらに意味的にグループ化する単位。Epicが存在する場合にのみ存在しうる。必須ではない。

- **Epicとの違い**:
  Featureは同一Epic内での意味的なサブカテゴリ。Epicを越えてFeatureが存在することはない。
- **属性**: タイトル / 本文（概要・スコープ）/ 親Epicへの参照 / 子PBIへの参照。

### 2.6 PBI (Product Backlog Item)

Featureに属する価値の最小単位。完了条件（AC）が定義され、複数のWPに分解される。
Featureが存在しない場合はPBI単体で管理する。

- **要件**: 進捗状態の管理、サイズの見積と実績の記録、スプリントへの所属、親Featureによる分類。
- **属性**: タイトル / 本文 / 状態（Idea / Todo / InProgress / Done）/ サイズ見積（XS / S / M / L /
  XL）/ サイズ実績（XS / S / M / L / XL）/ 所属スプリント / 親Feature参照 / 子WP参照。

### 2.7 WP (Work Package)

PBIを分解した最小の実装単位。1セッションで1つのWPを完了させることを原則とする。

- **要件**: 親PBIへの所属、effortの計画と実績の記録、乖離理由の記録、実行順序の管理。
- **属性**: タイトル / 本文（AC達成エビデンス）/ 親PBI参照 / effort初期見積 / effort計画値 /
  effort実績 / 乖離理由 / 順序 / 状態（Todo / InProgress / Done）。

### 2.8 Review

スプリント終了時にSprint Goalに対する達成状況を検証・承認するための概念。スプリントごとに1つ。
エビデンス置場として機能し、結果は本文に記録する。

- **要件**: レビュー結果の詳細記録。
- **属性**: タイトル / 本文（レビュー結果の詳細）/ 所属スプリント / 変更履歴。

### 2.9 Retrospective

スプリント終了後にプロセスや協働の質を振り返るための概念。スプリントごとに1つ。

- **要件**: effort集計、予実差分析、スプリントメトリクスの構造化記録。
- **属性**: タイトル / 本文（KPT（Keep / Problem / Try /
  Advise）とスプリントメトリクス5指標の人間向け表示）/ 所属スプリント / スプリントKPT /
  スプリントメトリクス（Goal Achievement Rate / Estimation Accuracy / Quality Integrity /
  Collaboration Discipline / Velocity）。

## 3. 状態遷移

状態は原則として単方向（Idea → Todo → InProgress → Done）で遷移する。

### 3.1 PBI の状態遷移

```
Idea(発案) → Todo(コミット) → InProgress(着手) → Done(完了)
```

| 遷移              | トリガー操作 | 備考                     |
| ----------------- | ------------ | ------------------------ |
| Idea → Todo       | コミットする | スプリント計画時         |
| Todo → InProgress | 着手する     | 最初のWPが着手された時   |
| InProgress → Done | 完了する     | 全WP完了時またはPO承認時 |

### 3.2 WP の状態遷移

```
Todo(定義) → InProgress(着手) → Done(完了)
```

| 遷移              | トリガー操作 | 備考                 |
| ----------------- | ------------ | -------------------- |
| Todo → InProgress | 着手する     | セッション計画承認時 |
| InProgress → Done | 完了する     | PO承認時             |

> 各遷移のトリガーは、AIが対象を検索・確認・操作して実現する。抽象的な「自動」表現は用いない。

## 4. 指標系

AI開発における見積り・評価は、コード量ではなく**「人間の介入（ハンドオフ）がどれくらい発生しそうか」**を基準とする。

### 4.1 Size（T-Shirt Size）

PBIのサイズ見積。ウェイト換算でベロシティ算出に用いる。

| サイズ | ウェイト | 判断基準の目安                                                 |
| ------ | -------- | -------------------------------------------------------------- |
| **XS** | 1        | 極小タスク。人間の確認不要でエージェントが即座に完了可能。     |
| **S**  | 2        | 明確な単一タスク。エージェントがほぼ自律で完了可能。           |
| **M**  | 3        | 複数ステップ。1〜2回の人間による確認・方針修正が必要。         |
| **L**  | 5        | 設計判断を含む。複数回の議論やレビューが必要な複雑なタスク。   |
| **XL** | 8        | アーキテクチャ変更。不確実性が高く、複数セッションにまたがる。 |

### 4.2 Effort（介入回数）

セッションレベルでの労力。**「AIに対する人間の介入回数（具体的な数値）」**として測定する。
3点見積もりでボトルネックを分析する。

| 見積り     | タイミング                       | 定義                                                         |
| ---------- | -------------------------------- | ------------------------------------------------------------ |
| 計画前見積 | WP作成時またはWP選択時           | WPの記述・要求定義から想定される介入回数                     |
| 計画後見積 | 計画完了・PO合意時               | 計画前見積以降の計画中の介入も含む最終的な想定総介入回数     |
| 完了時実績 | セッション終了・メトリクス記録時 | セッション開始から完了までに実際に発生したPOの介入回数実績値 |

### 4.3 介入（Intervention）

Effort（介入回数）を定義する上で、何を「介入」と数えるかを規定する。

以下の行為がPO（人間）から発生した場合に、介入回数を `1回` としてカウントする。

- **意図の修正指示（やり直し）**:
  AIが意図を誤認して実装したため、「そうではなく、このように修正して」と再指示すること。
- **制約・ルールの違反指摘**: 計画外ファイルの編集や絶対パスの使用など、規律の逸脱を指摘すること。
- **アプローチの軌道修正**: 設計のトレードオフ議論を経て、実装方針を大がかりに変更すること。

※
プロセスの単なる進行指示（「次へ」「進めて」など）や、AIからの純粋な質問に対する1往復の回答は介入に含まない。

### 4.4 Velocity（規模消化力）

スプリントで完了したPBIの総ウェイト（Σ）。見積と実績の乖離により規模消化力を測る。 Velocity
は1〜5スコアではなくウェイト換算値（Σ）で記録する。

### 4.5 Metrics（メトリクス）

評価の測定値には、スプリントレベルとセッションレベルの2種類がある。

#### スプリントメトリクス（5指標）

スプリント終了時に記録する5指標。各指標は1〜5スコア（Velocity除く）と戦略的ナラティブで記録する。

1. **Goal Achievement Rate**（ゴール達成率）: Sprint Goalに対する達成度。
2. **Estimation Accuracy**（見積もり精度）: 見積Tシャツサイズと実労力の一致度。
3. **Quality Integrity**（品質健全性）: 実装品質とガードレール遵守度。
4. **Collaboration Discipline**（協働品質とプロセス規律）: 協働プロセスの規律。
5. **Velocity**（規模消化力）: 完了PBIの総ウェイト（Σ）。

#### セッションメトリクス（4指標）

セッション終了時に記録する4指標。各指標は1〜5スコアと戦略的ナラティブで記録する。

1. **Intent Alignment**（意図の整合率）: AIの実装がPOの意図に沿っていたか。
2. **Constraint Adherence**（制約遵守度）: 計画やルールの制約が遵守されたか。
3. **Context Extraction**（コンテキスト説明の質）: コンテキストを適切に説明・把握できたか。
4. **Work Size Stability**（作業単位の安定性）: 作業単位（WP）の粒度が適切だったか。

## 5. 品質要件

### 5.1 Acceptance Criteria（AC）

受入基準（AC）はWPの配下にリスト形式で記述する。すべてのACを満たした時点でPBIが完了可能となる。

- AC は `- [ ] AC: <内容>` のチェックボックス形式で記述する。
- すべてのACを満たしたことがPBIの完了条件となる。

### 5.2 KPT

振り返り手法（Keep / Problem / Try / Advise）。スプリント・セッションの終了時に記録する。

- **Keep**: 継続すべき良かった点。
- **Problem**: 改善すべき問題点。
- **Try**: 次回試すべき改善策。
- **Advise**: アドバイス（任意）。

### 5.3 品質ガードレール

AIが自律的に行動する中で、意図しないデータ更新や計画の逸脱が発生するのを防ぐ一連の仕組み。

- **計画先行の原則**: AIは作業開始前に計画を作成し、人間の承認を得る。計画のない実装は禁止。
- **チェックポイント進行**:
  作業はAC単位のチェックポイントで進行。各チェックポイントに明確な完了条件を定義。
- **状態の永続化**: 各チェックポイントが完了するたびに、その時点の作業状態を保存。
- **構造の強制**: 作業は決められた進行手順（計画 → 着手 → 実装 → 検証 → 完了報告）に従う。
- **人間による承認ゲート**: 計画の承認・完了の判断・次の工程への進行は、必ず人間の承認を経由。
- **物理的な品質バリア**:
  全ての変更がリモートへ送信される前に、自動で書式・静的解析・型検査・テストが実行され、一つでも失敗すれば送信がブロックされる。
